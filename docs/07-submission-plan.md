# 차록 · 공모전 기획서

2026-11-15 KST / 2026-11-14 UTC · 설계 v0.3 · **기획 및 브라우저 UX 시안, Android 앱 미구현**

이 문서는 공식 접수양식의 작품 소개 1~8번에 대응합니다. [양식에 옮긴 DOCX 초안](submission/charok-application-draft.docx)은 개인 정보·동의·서명 미작성으로 아직 제출 완료본이 아닙니다. 현재 구현 범위와 UI는 이 문서와 [08](08-ux-ui-spec.md), [09](09-demo-delivery-plan.md)를 우선하며, 이전 문서는 조사 이력으로 보존합니다.

## 1. 앱 한 줄 소개

**“이럴 때만 이상해요”를, 정비사와 함께 확인할 수 있는 기록으로.**

차록은 운전자가 느낀 증상과 실제 확보한 직전 최대 60초부터 종료까지의 차량 상태를 연결해, 정비 상담을 돕는 Pleos 앱입니다.

## 2. 기획 배경

차량을 잘 모르는 운전자는 소음·진동·공조 이상을 경험해도 당시 상황을 정확하게 설명하기 어렵습니다. 간헐적인 증상이 정비소에서 재현되지 않으면 고객의 기억과 정비사의 현재 진단 사이에 빈틈이 생깁니다. 차록은 발생 순간에 말을 남기고, 그 전후의 확보 가능한 차량 상태를 함께 보존합니다.

주 고객은 차량 지식이 적은 운전자, 차를 함께 쓰는 가족, 간헐적 증상을 겪는 운전자입니다. 두 번째 사용자는 정비사입니다. 기존 현대 리모트케어와 정비 진단 장비를 대체하지 않습니다. 정비소 밖에서 운전자가 체감한 순간을 상담 자료로 만드는 흐름의 효용을 검증합니다. 독창성·시간 절감·수리비 절감은 아직 검증되지 않은 가설입니다.

## 3. 주요 기능과 차량 특화 요소

1. **이전 상황까지 남기는 기록:** 사용자가 정차 중 기록 준비를 켜면 지원 데이터의 최근 60초만 임시 보관합니다. 시작 명령을 받으면 실제 확보된 과거와 이후 관측을 같은 기록에 연결합니다. 준비 전 과거, 끊긴 센서 값은 만들어 채우지 않습니다.
2. **운전 중에는 짧은 대화:** “증상 기록해 줘”, 증상 설명, “지금이야”, “기록 종료해 줘”를 처리합니다. 운전자 진술과 센서 관측을 구분합니다. 준비·음성·차량 수집의 상태를 별도로 관리합니다.
3. **한눈에 보는 기록 상태:** 순정 차량 정보와 내비를 유지하고 앱 패널에 기록 상태·핵심 문장·종료를 표시합니다. 긴 기록 확인과 수정·공유는 정차 후 진행합니다. 창 위치는 시스템 정책에 따릅니다.
4. **정비 상담 카드:** 원문, 증상 순간, 실제 확보된 상태, 누락 구간을 한 장으로 묶습니다. “핸들을 돌릴 때 소리가 났다는 사용자 설명”을 “조향 장치 고장”으로 바꾸지 않습니다.
5. **고객이 선택하는 인계:** 먼저 로컬 보고서 내보내기를 구현합니다. 공유는 사용자가 범위를 확인하고 선택한 자료에만 적용합니다. 자동 예약·업체 수신은 별도 API와 검증을 거친 확장입니다.

차량 특화성은 휴대폰 음성 메모보다 넓은 차량 관측과 동일 시간축의 연결, 순정 내비와 함께 쓰는 UI, 실제 운전 상태에 따른 조작 제한에 있습니다. 전체 CAN·DTC·기계음·카메라 수집을 제공한다고 주장하지 않습니다.

## 4. 대표 사용 시나리오

**시연 조건:** 정차 상태의 재현 시나리오. 차량 상태는 TEST 또는 실제 Pleos Console/SDK로 각각 표시합니다. 서로 다른 검증 수준을 섞어 실차 기록처럼 보이지 않게 합니다.

1. 운전 전 “기록 준비”를 켭니다. 앱이 받은 구간만 준비량으로 표시됩니다.
2. 운전자가 “차록, 증상 기록해 줘. 핸들을 돌릴 때 앞쪽에서 덜컥 소리가 나요”라고 말합니다.
3. 기록이 실제 시작된 뒤 “차량 증상을 기록합니다. 언제 소리가 나나요?”라고 짧게 묻습니다. 이미 설명에 있는 내용은 다시 묻지 않습니다. 위치가 확인된 경우에만 지역을 안내합니다.
4. “지금이야. 방금 또 났어.”를 그 시점의 **사용자 표시**로 저장합니다. 소음을 센서로 검출했다고 표시하지 않습니다. 한 번에 한 질문만 하고 사용자가 대답하지 않으면 계속 질문하지 않습니다.
5. “기록 종료해 줘.” → 관측 중지 → 저장 중 → DB commit 및 재조회 이후 저장 완료. 실패하면 같은 기록으로 재시도합니다.
6. 정차 후 요약을 확인합니다. “반복되는 증상이라면 이 기록으로 정비 상담을 받아보세요.”라고 제안합니다. 차가 안전하거나 특정 부품이 고장 났다고 단정하지 않습니다.
7. 상담 카드를 확인·내보냅니다. 별도로 선택한 실제 센터의 확인된 좌표가 있으면 사용자 요청에 따라 순정 내비에 경로를 요청합니다. 예약 확정과 길 안내는 다른 상태입니다.

**확장 시나리오:** 승인된 원음 채집, 실제 센터 일정 조회·예약·자료 전달, 스캐너에서 자동 열람. 공개 지원 경로가 확인될 때 구현하며 이번 시연의 필수 의존성에서 제외합니다.

## 5. 개발 계획 및 SDK

Kotlin·Compose·Room을 사용해 기록 도메인과 SDK 어댑터를 분리합니다. TEST 입력과 SDK 입력은 같은 기록 엔진을 통과하되 출처를 영구 보존합니다. 앱은 차량 설정을 제어하지 않고 필요한 공개 조회 API만 사용합니다.

| 구성 | 개발 범위 | 현재 근거와 완료 조건 |
| --- | --- | --- |
| Vehicle 2.3.2 | 기어·조향·브레이크·공조 등 지원 필드 구독 | 선정 메서드 정적 권한 조사 있음. capability/권한/실제 callback별 확인 필요. PRIVATE 권한 제외 |
| Gleo Interface | 시작·설명 추가/순간 표시·종료의 3개 action | 최대 3개, asking·7초 timeout 문서 확인. 실제 매핑/재호출/한국어 대화 미검증 |
| SpeechToText 3.3.1 | 앱 내 공식 ON_DEVICE 인식 | 차량 마이크→텍스트 경로 문서 확인. 실제 마이크와 보유 PCM 주입 시험 분리 |
| TextToSpeech 3.3.1 | 짧은 응답, 대화 차례 관리 | Gleo 발화와 중복되지 않게 한 경로만 소리 출력. 실제 실행 필요 |
| FusedLocation 1.1.3 | 동의한 위치를 기록에 연결 | 수신 시각·정확도·가용 상태 확인. 도로명/날씨는 별도 데이터가 없으면 생략 |
| NaviHelper 3.0.5 | 확인한 센터 좌표로 경로 요청 | 요청/완료 callback/순정 핀을 각각 검증. 자동 도착 판정 없음 |
| Room·보고서 | 60초 버퍼·세션 저장·요약·내보내기 | 실제 DB 재조회·새 PID 복원·선택 범위와 내보낸 내용 일치 |

앱 자체 기록/저장 흐름은 Cloud에서 구현·검사합니다. Mac Pleos 한 대에서 실제 SDK·마이크·분할 화면·순정 내비를 검증합니다. 장비가 연결되지 않으면 TEST 프로토타입 수준을 명시합니다. 이번 문서와 브라우저 시안은 APK나 Pleos 실행 증거가 아닙니다.

## 6. 기대효과와 발전 가능성

운전자는 증상을 설명할 단서를 확보하고 정비사는 발생 조건을 질문할 출발 자료를 얻습니다. 우선 원문 메모와 차록 요약을 비교해 조건 누락, 요약 왜곡, 추가 질문, 상담에 쓸 의향을 확인합니다. 예상 MAU·Retention 수치를 근거 없이 만들지 않습니다. 저빈도 문제 해결 서비스이므로 일일 접속보다 필요 순간 기록 완결률과 상담 활용도를 우선 봅니다.

향후 동의 기반 센터 자료 접수와 예약, 지원 계약에 따른 GDS 연동을 검토합니다. 수익 모델은 검증된 상담 효용을 전제로 한 정비 접수 도구 또는 차량 서비스 연계 가설입니다. 실제 제휴·매출은 없습니다.

## 제출 전

공식 접수양식과 서명한 동의서가 필수입니다. 공개 저장소에 참가자의 연락처·서명·개인정보를 올리지 않습니다. 선택 APK를 제출한다면 공식 안내에 맞는 **설치·실행 가능한 release 빌드**로 검증하고 서명 종류·해시·코드 커밋을 기록합니다. unsigned APK를 실행 가능한 제출본으로 표시하지 않습니다. 앱마켓 출시 심사와 공모전은 구분합니다.
