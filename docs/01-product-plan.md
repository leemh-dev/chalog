# 차록 기획서

버전 0.2 · 2026-11-14 UTC · 상태: 기획/조사, 미구현

> 후속 설계 v0.3: [07·공모전 기획서](07-submission-plan.md), [08·UX/UI](08-ux-ui-spec.md), [09·제출 실행 계획](09-demo-delivery-plan.md)을 현재 범위로 우선합니다. 아래는 요구와 조사 배경을 보존한 이력입니다.

> 최신 UX 요구는 음성 시작→3영역→Gleo 대화/순간표시→조건부 원음채집→요약/상담권유→승인 후 예약·자료전달→내비 안내다. [전체 시나리오 기술 재검토](05-conversation-scenario-feasibility.md)에 구현 경로와 차단/미검증을 구분했다. 원음과 실제 예약을 현재 가능으로 확정하지 않는다.

## 1. 서비스 정의

**운전자가 이상 증상을 느낀 구간의 전후 상황을 보존하고, 고객과 정비사가 같은 기록을 보며 대화하는 서비스.**

운전자가 “증상 기록해 줘”라고 하면 실제 확보한 직전 1분부터 데이터를 보존하고, “종료해 줘”라고 하면 수집을 멈추고 저장합니다. 음성으로 설명한 증상과 확인 가능한 차량 상태·위치·환경 자료를 시간순으로 묶습니다.

프로젝트명은 **차록(CHAROK)**, 소개 문구는 **“증상이 생긴 그 순간부터, 정비사와의 대화까지.”**입니다. 이름 중복·상표는 확인하지 않았습니다.

## 2. 해결하려는 문제

- 간헐적 소음·진동·공조 이상은 정비소 방문 때 재현되지 않을 수 있습니다.
- 운전자는 당시 어떤 조작을 했고 어떤 상태였는지 정확히 기억하기 어렵습니다.
- 차량 지식이 부족하면 “이상한 소리가 났다” 이상의 설명이 어렵습니다.
- 정비사는 고객 설명, 현재 스캐너 진단, 과거 발생 상황을 따로 맞춰야 합니다.

차록은 운전자의 체감 증상과 당시 확보한 관측을 연결해 상담의 출발 자료를 만듭니다. 고장 원인을 확정하거나 정비사의 진단을 대신하는 기능은 초기 범위에 넣지 않습니다.

## 3. 대상 사용자와 가치 가설

주 고객은 차량 지식이 적은 운전자, 차량 공동 이용자, 간헐적 증상을 겪는 운전자입니다. 정비사는 기록을 읽고 추가 질문과 재현 조건을 확인하는 두 번째 사용자입니다.

핵심 가설은 **단순 음성 메모보다 발생 구간과 차량 상태를 연결한 기록이 정비 문진에 유용하다**는 것입니다. 아직 운전자·정비사 인터뷰로 입증하지 않았습니다. 앱 사용 빈도나 수리비 절감률을 검증된 성과로 제시하지 않습니다.

## 4. 대표 시나리오

아래 시각과 증상은 설계 예시이며 실제 차량 기록이 아닙니다.

1. 운전자가 앱에서 기록 준비를 켭니다. 지원된 차량 상태만 최근 60초의 임시 순환 버퍼에 유지합니다.
2. 14:32:00, 운전자가 “증상 기록해 줘. 핸들을 돌릴 때 앞쪽에서 덜컥 소리가 나”라고 말합니다.
3. 앱은 실제 확보한 14:31:00 이후 데이터와 발화를 같은 기록 세션에 연결하고 이후 수집을 계속합니다.
4. 14:33:20, “종료해 줘”가 처리되면 수집을 멈추고 저장합니다. 이 예시의 최대 구간은 140초입니다.
5. 정차 후 운전자는 원문·관측·누락 구간을 확인하고 필요한 설명을 보완합니다. 저장 중/완료/실패를 구분합니다.
6. 정비소에서 고객은 공유할 기록을 선택합니다. 정비사는 타임라인을 보며 “이때 소리가 났나요?”, “공조를 켰을 때 반복됐나요?”라고 대화합니다.
7. 정비소 스캐너가 제공한 DTC나 freeze frame이 있다면 별도 출처·시각을 유지하며 함께 비교합니다.

음성 명령의 앱 전달 경로는 공식 STT/Gleo 연동을 실제 검증해야 합니다. 문구를 정했다고 순정 음성 호출이 자동 지원되는 것은 아닙니다.

## 5. 기록 방식

### 직전 1분

명령 전에 SDK callback을 실제로 받고 있어야 합니다. 준비 후 20초만 지났으면 최대 20초만 남길 수 있습니다. 앱 종료/권한 차단/SDK 끊김 구간은 공백입니다. 마지막 값 하나를 반복해 과거 데이터를 만든 것처럼 표시하지 않습니다.

명령 발화 시각, STT 결과 수신 시각, 앱의 trigger 시각을 구분합니다. 발화 시작 시각을 확보하지 못하면 결과 수신 시각을 기준으로 한 구간임을 표시하며 정확히 발화 전 60초를 보장하지 않습니다.

### 종료와 저장

권장 기본값은 “종료해 줘”가 세션 기록과 준비 버퍼를 모두 중지하는 것입니다. 종료 후 준비 유지 옵션은 추후 UX 결정 사항입니다. 종료 명령 전 무제한 저장을 피하도록 시간/용량 상한과 실패 안내를 설계하며, 실제 수치는 측정 후 정합니다.

명령 인식 실패 시 종료됐다고 표시하지 않습니다. 앱 종료/권한 철회/저장소 부족으로 중단되면 중단 이유와 마지막 저장 시점을 남깁니다. 다음 실행 때 수집/마이크를 자동 재개하지 않습니다.

## 6. 데이터 범위

| 구분 | 기록 내용 | 해석 원칙 |
| --- | --- | --- |
| 사용자 설명 | 소음·진동·위치·조작·횟수 등 발화와 수정 내용 | 사용자 진술이며 센서 확인으로 승격하지 않음 |
| 차량 상태 | 지원되는 기어·조향각·브레이크 상태·주행거리·공조·일부 경고 등 | 필드별 API·권한·실제 수신 확인. 값/단위/시각/공백 보존 |
| 위치 | 권한과 지원이 확인된 위치·시각·신뢰도 | 마지막 위치/저신뢰/수신 공백을 표시 |
| 도로 정보 | 위치를 지도 자료와 연결한 도로명·유형 등 | 지도 매칭 결과이며 실제 노면·차선 실측과 구분 |
| 날씨 | 위치·시간에 맞는 외부 관측 자료가 확보된 경우 | 외부 자료 출처·관측 시각 표시. 차량 자체 실측과 구분 |
| 정비 진단 | 정비사가 별도로 확인한 DTC·진단 메모 등 | 취득 경로·조회 시각을 분리. 앱의 과거 기록과 혼동하지 않음 |

‘주변 환경·도로·운행의 모든 정보’는 장기 비전입니다. 초기 제품은 **공개 SDK로 확인 가능한 상태와 허용된 위치·환경 자료**로 범위를 명시합니다. 카메라 영상, 실제 기계음 분석, 진동, RPM, raw CAN, 전체 DTC 수집은 제공 경로 확인 없이 약속하지 않습니다.

## 7. 화면과 조작

- **준비 화면:** 큰 준비 버튼, 실제 확보한 버퍼 길이, 지원 필드/차단 상태
- **기록 중:** 경과 시간, 직전 구간 확보 범위, 짧은 사용자 증상, 명확한 종료 상태
- **저장 결과:** 저장ACK·중단 이유·재시도 상태, 정차 후 상세 열기
- **고객 타임라인:** 발화/관측/공백/외부 자료를 출처별로 표시
- **정비사 화면:** 선택한 구간의 요약과 타임라인, 원문, 별도 진단 메모

순정 차량 정보·내비를 가리지 않는 앱 패널을 전제로 합니다. Pleos 분할 자동 제어/임의 오버레이는 핵심 의존성에서 제외합니다. 상세 수정·기록 목록·공유는 정차 상태에서만 제공합니다. 주행 또는 상태 미확인 시 조작을 제한하고, 초기 시연은 정차 상태에서 완결합니다. 주행 중 음성 시작/종료는 실제 호출 경로와 운전 제한 정책 검증 후 연결합니다.

## 8. 정비소 인계

### 초기 구현

고객이 선택한 한 건을 정비사가 열어 함께 검토합니다. 로컬 보고서/PDF부터 확인하고, 필요하면 고객 동의 기반 QR/웹뷰어를 구현합니다. 공유 대상 앱/기기/네트워크가 실제로 동작하는지 확인해야 합니다. QR 전송·만료·접근 제한은 구현 전까지 미완료입니다.

### 최종 목표

**스캐너 연결 → 차량·접수건 식별 → 고객 공유 동의 확인 → 해당 기록 조회 → 스캐너 진단과 함께 검토.**

스캐너가 ECU와 통신하는 것과 Pleos 앱 저장소를 읽는 것은 별도 경로입니다. GDS/GIT/현대의 지원 인터페이스·인증·기록 포맷 연동이 필요하며 현재 공개 연동은 미확인입니다. VIN만 알면 누구나 기록을 열 수 있게 하지 않습니다. [세부 분석](02-sdk-feasibility.md).

## 9. 저장·개인정보·AI 원칙

- 같은 session ID 아래 사용자 원문, 관측, 확인/수정 이력, 저장 상태를 보존합니다.
- 각 관측의 값·단위·출처·수신 시각·가용 상태를 저장합니다. 비동기 조회 묶음을 원자적 ECU snapshot이라고 부르지 않습니다.
- 중간 STT 결과, 화면 변경, 저장 성공을 구분합니다. 실제 SQLite commit/재조회/새 PID 복원을 확인합니다.
- 준비 버퍼는 한정된 시간만 유지하며 선택하지 않은 과거는 만료시킵니다. 차내 주변 음성·원시 PCM·전체 이동 경로를 기본으로 영구 보관하지 않습니다.
- 위치는 선택 동의 후 취득하고 기록 공유는 별도 선택입니다. 삭제·공유 취소/만료 정책을 구현 시 정의합니다.
- AI는 발화의 구조화·요약·유사 기록 정리를 돕되 원문을 유지합니다. 사용자 확인 없는 고장 원인/안전 주행 판정은 만들지 않습니다.
- 경고가 없거나 수신되지 않았다고 차량 정상이라고 결론 내리지 않습니다. OEM 경고와 설명서를 대체하지 않습니다.

## 10. 차별성과 성공 판단

현대 리모트케어의 이상 감지/상담, GDS의 기록 재생/보고서 첨부는 기존 기능입니다. ‘정비 기록이 처음’이라고 주장하지 않습니다. 차록의 가설은 **정비소 밖에서 발생하는 간헐적 증상을 운전자가 전후 구간과 함께 쉽게 보존하고 상담으로 연결하는 흐름**입니다. 동일 서비스가 전혀 없다는 증거는 확보하지 않았습니다.

기술 완료 기준은 실제 SDK 구간 확보, 공백/권한 오류의 정확한 표시, 저장·재시작 복원, 선택 기록의 정비사 열람입니다. 제품 검증은 운전자/정비사에게 원문 메모와 요약을 비교하게 해 발생 조건 누락·추가 질문·요약 왜곡·재사용 의향을 확인합니다. 운전자 5명/정비사 3명은 제안 표본이며 실제 실시 결과가 아닙니다.

## 11. 범위

초기 목표는 Pleos 앱 기능 검증과 실제 동작 시연입니다. 앱마켓 출시·출시 서명·실차 검증은 초기 완료 조건이 아닙니다. 스캐너 자동 연동은 확장 목표로 유지하며 첫 버전의 완료로 표시하지 않습니다.

현재 차록 저장소에는 앱·서버·정비사 뷰어가 없습니다. 다음은 [개발 계획의 단계0](03-development-plan.md)에 따라 실제 SDK 실행부터 검증합니다.
